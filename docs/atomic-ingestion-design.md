# Atomic Ingestion Pipeline Design

## Purpose

The early document pipeline should be decomposed into stages with one kind of
responsibility, one narrow output contract, and one recognizable failure mode.
The pipeline must remain a LangGraph workflow. LLM stages may interpret source
content, but deterministic code owns source preservation, edit application,
reconstruction, and validation.

The governing rule is:

> Each stage makes one kind of decision. No LLM stage silently drops source
> content or applies unvalidated page-wide rewrites.

## Design principles

- Preserve the original OCR/transcription as the source of truth for
  reconstruction and provenance.
- Use 1-based line-addressed edits and spans.
- Let LLMs propose narrow decisions or edits rather than rewrite whole pages.
- Keep deterministic validation immediately after every LLM boundary.
- Prefer conservative preservation over speculative correction or inference.
- Keep formatting separate from fidelity correction and knowledge extraction.
- Keep structural parsing separate from semantic document classification.
- Keep raw durable records separate from rebuildable derived graph data.
- Keep model and stage boundaries explicit in LangGraph.

## Target early pipeline

```text
OCR/transcription
    ↓
correction detection and proposal
    ↓
deterministic correction application
    ↓
formatting normalization
    ↓
source-position-aware structural segmentation
    ↓
ambiguous block classification
    ↓
deterministic AST reconstruction
    ↓
semantic document stages
```

The first implementation should not introduce every possible specialist. The
architecture is intentionally incremental: begin with the highest-value
boundaries, measure failures, and add specialists only when tests show that a
single narrow stage remains unstable.

## Corrector decomposition

The corrector checks fidelity against the page image. Its authority is the
image, not subject-matter knowledge or preferred notation.

### Detection

An anomaly detector identifies lines or regions that deserve review. It does
not rewrite text. Candidate signals include:

- suspicious mathematical symbols or delimiters;
- unusual digits, signs, exponents, subscripts, or fractions;
- broken words or duplicated text;
- missing or duplicated content;
- suspicious indentation, table placement, or line order;
- possible missing image placeholders or page content.

The detector may be deterministic, multimodal, or hybrid. Its output is a
small set of line or region identifiers.

### Specialized proposals

The first useful specialist is a mathematical transcription verifier. It
reviews only flagged mathematical regions and proposes precise edits for:

- exponents and subscripts;
- signs, inequalities, and negation;
- fractions, radicals, and grouping;
- Greek letters and other symbols;
- equation extent and attachment;
- matrix, table, and aligned-equation positions.

A prose verifier can review flagged prose regions for clear OCR errors such as
missing words, duplicated words, character substitutions, and punctuation
errors. It must not stylistically rewrite the source.

A layout/content verifier can review structural fidelity: images, captions,
headers, footnotes, tables, lists, fragments, and possible missing or
duplicated lines.

Specialists should either own disjoint regions or produce proposals for one
adjudicator. Independent whole-page rewrites are not allowed.

### Adjudication and application

An adjudicator resolves overlapping or conflicting proposals. It must reject
changes that are not settled by the image, changes that alter source meaning,
and edits that overlap incompatibly.

The program applies the final line edits deterministically. It validates:

- 1-based indexes;
- in-range indexes;
- no duplicate indexes;
- stable ordering;
- untouched lines remain unchanged;
- no forbidden formatting changes enter the correction pass.

The corrector output remains corrected transcription text, not a rewritten
page generated by the model.

### Corrector flow

```text
page image + OCR transcription
    ↓
anomaly candidates
    ↓
math verifier ───────┐
prose verifier ──────┼──→ edit adjudication
layout verifier ─────┘
    ↓
validated line edits
    ↓
deterministic application
```

The initial implementation may combine detection and proposal in one
multimodal corrector, provided the output remains line-addressed edits and the
program applies and validates them deterministically.

## Formatter decomposition

The formatter normalizes representation without changing the author's
meaning. It is allowed limited notation-aware reasoning, but it is not a
fidelity corrector and does not extract knowledge.

### Delimiter normalization

Normalize recognized delimiters without changing the expression:

```text
\(x\)       → $x$
\[x\]       → $$x$$
```

Balanced-delimiter checks should be deterministic.

### Display-math normalization

Identify standalone equations or LaTeX display environments that need
canonical display delimiters. Preserve every mathematical token and its order.

### Inline-math normalization

Identify mathematical expressions embedded in prose and delimit only the
expression, not the surrounding sentence. This is more semantic than simple
delimiter replacement and should remain a separate contract.

### Currency and delimiter disambiguation

Distinguish currency from mathematical dollar delimiters:

```text
The cost was $15.
The solution is $x = 15$.
```

Currency must not be consumed into a math span.

### Unicode notation normalization

Convert mathematical Unicode notation to LaTeX where the character is clearly
notation rather than ordinary language. Do not alter names, words, footnote
markers, or code. This pass changes encoding, not mathematical meaning.

### Markdown normalization

Normalize Markdown representation such as:

- heading markers;
- list markers and indentation;
- table separators;
- code fences;
- emphasis markup;
- block spacing;
- exercise part-marker decoration.

Formatting must not renumber identifiers, change figure placeholders, rewrite
mathematics, or add or remove substantive content.

### Formatter validation

After formatting, validate line edits and the resulting text:

- edits are unique, ordered, and in range;
- figure placeholders survive exactly;
- code and verbatim regions survive exactly;
- math delimiters are balanced where required;
- currency was not mistaken for math;
- untouched content is unchanged;
- the result is parseable by the structural parser.

### Formatter flow

```text
corrected transcription
    ↓
delimiter normalization
    ↓
display-math normalization
    ↓
inline-math normalization
    ↓
currency and Unicode notation handling
    ↓
Markdown structure normalization
    ↓
validated line edits and formatted transcription
```

The first implementation may combine related math operations, but it should
retain the conceptual boundary between representation normalization and
content correction.

## Extractor decomposition

The extractor converts formatted Markdown into structural AST nodes. Its
central invariant is that every nonblank source line is preserved exactly once
before any later semantic filtering.

### Source-position-aware segmentation

Use an established Markdown parser that exposes source positions rather than
hand-rolling a complete Markdown state machine. The parser should identify or
support:

- headings;
- paragraphs;
- fenced code;
- lists;
- tables;
- images;
- block quotes where relevant;
- source line ranges.

KMS-specific adapters may add narrow support for LaTeX display math, OCR image
placeholders, footnotes, and other source conventions. The adapter must not
become a second general-purpose Markdown parser.

The parser produces candidate blocks with source ranges. The program slices
content from the original source lines, never from normalized or model-written
text.

### Candidate coverage

Before any LLM classification, deterministic validation requires:

- every nonblank source line belongs to a candidate;
- candidates are ordered and non-overlapping;
- candidates are in range;
- blank separator lines may be omitted;
- blank lines inside a recognized structure remain part of that structure;
- no candidate contains only blank lines.

A missing line is a segmentation or parser-adapter failure, not a reason for an
LLM to invent replacement text.

### Ambiguous block classification

The parser can assign obvious types directly. An LLM may classify ambiguous
candidate blocks as:

- paragraph;
- header;
- math;
- code;
- list;
- table;
- image;
- note;
- caption;
- bibliographic;
- furniture.

The LLM receives ordered candidate identifiers and source content. It returns
candidate identifiers and types, not unrestricted line numbers or rewritten
text.

When uncertain between content and furniture, preserve the content as a
paragraph. Furniture removal is a later, auditable decision.

### Special semantic classifiers

Furniture detection is distinct from Markdown parsing. It identifies running
heads, folios, repeated titles, licence text, access URLs, publisher notices,
and colophons.

Caption and figure association is also distinct. It may associate a caption
with a preceding image without changing the underlying source blocks.

These classifiers may be added after basic segmentation is stable.

### Merge and seam resolution

A resolver may merge adjacent parser candidates when a structure was split by
OCR or a page seam. It may not merge arbitrary distant blocks or delete a
candidate. All merges preserve the original source order and text.

Page-boundary merging remains separate from ordinary page extraction. A seam
resolver can decide whether the tail of one segment and the head of the next
are halves of one block, after which deterministic code performs the merge.

### AST reconstruction

The program combines:

```text
source ranges
final candidate types
approved adjacent merges
```

and reconstructs AST nodes from the original lines. The LLM never supplies the
stored block text.

Final validation repeats the coverage checks and additionally verifies:

- nonempty output for nonblank input;
- known node types only;
- ordered, non-overlapping ranges;
- exact one-time coverage of every nonblank source line;
- no blank-only nodes;
- no dropped or duplicated source content.

### Extractor flow

```text
formatted Markdown
    ↓
source-position-aware Markdown parser
    ↓
deterministic candidate blocks
    ↓
ambiguous block classifier
    ↓
furniture and caption classifiers
    ↓
adjacent merge/seam resolution
    ↓
deterministic AST reconstruction
    ↓
strict coverage validation
```

The simplified single-call extractor remains a valid short-term experiment,
but parser-backed segmentation is the target architecture if prompt
simplification does not remain reliable across the fixture corpus.

## Windowing and context

Token-bounded windows are useful after safe units have been identified. Do not
split arbitrary lines when the model needs structure across them.

- Pack complete parser candidates up to a target token budget.
- Keep code, tables, display math, and other atomic structures together.
- Use small read-only context overlap where a boundary requires it.
- Give each window explicit ownership; context lines cannot be edited or
  emitted twice.
- Use stable global line or candidate identifiers.
- Reconcile only adjacent windows or seams.

The model's completion budget must fit the configured server context. Prompt
size, context overlap, and output budget must be considered together.

## Responsibility matrix

| Stage | Owns | Must not do |
| --- | --- | --- |
| OCR anomaly detection | suspicious regions | rewrite source text |
| Math correction | visual mathematical fidelity | alter prose or format |
| Prose correction | clear visual prose fidelity | fix equations or style |
| Formatter | representation and notation encoding | change meaning |
| Markdown parser | syntactic block positions | classify knowledge |
| Block classifier | ambiguous document types | invent spans or text |
| Furniture detector | page-apparatus classification | silently delete source |
| AST builder | exact reconstruction | use generated content |
| Fact extractor | explicit source facts | infer unstated claims |
| Triplet extractor | explicit relations | canonicalize or hallucinate |

## Rollout order

1. Keep strict line-edit and extractor coverage validation.
2. Evaluate the simplified extractor prompt against the fixture corpus.
3. Add parser-backed candidate segmentation if omissions recur.
4. Keep obvious formatter transformations deterministic where possible.
5. Split corrector specialists only after anomaly categories are measured.
6. Add furniture, caption, and figure association classifiers after basic AST
   construction is stable.
7. Keep all raw source records durable; rebuild only disposable derived graph
   structures.

## Success criteria

The early pipeline is successful when each stage can answer a focused audit
question:

- Correction: did the image settle every applied edit?
- Formatting: did representation change without changing meaning?
- Segmentation: where did every nonblank source line go?
- Classification: why was each candidate assigned its type?
- Reconstruction: was every stored node copied from source?
- Extraction: which source nodes support each explicit fact?

A stage failure should identify its own contract rather than appearing as an
opaque downstream graph or hub failure.
